# Mood Tracker — Developer Guide

Everything below is for engineers setting up, running, modifying, or
releasing this app. If you're looking for what the app does and who it's
for, see the main [README](../README.md).

## Stack

| Piece | Choice |
| --- | --- |
| Framework | Expo SDK 58, React Native 0.88, React 19.3 |
| Navigation | `expo-router` (file-based, tabs + stack) |
| Storage | `expo-sqlite` as a local document store (JSON payloads, WAL mode) |
| Charts | `react-native-svg` (hand-rolled multi-series line chart, no chart dependency) |
| Notifications | `expo-notifications`, scheduled on-device (no server) |
| Backup | `expo-file-system` + `expo-sharing` (local file, user-chosen destination) |
| Language | TypeScript, strict mode |

## Running it

Requires Xcode and Node 20+.

```bash
npm install
npm run ios          # builds a dev client and launches the iOS Simulator
```

`npm run ios` does a full native build the first time (a few minutes). After
that, `npm start` is enough — it boots Metro and attaches to the installed dev
client.

Useful scripts:

```bash
npm start            # Metro bundler for the dev client
npm run ios          # build + run on a simulator
npm run ios:device   # build + run on a physical iPhone over USB
npm run typecheck    # tsc --noEmit
npm run lint         # eslint
npm run check:store  # storage, migration and backup checks
npm run seed         # fill the simulator with plausible history
npm run release:ios  # signed .ipa for Transporter (see Releasing, below)
```

`check:store` compiles the storage layer and exercises it against an in-memory
stand-in for SQLite — no test runner and no extra dependencies. It covers the
migration from the old fixed-column table, which runs once and unattended on
the first launch after an upgrade, so it is the one piece that should not ship
on the strength of "it compiled".

The `ios/` and `android/` folders are generated by Expo prebuild and are
gitignored — change native config through `app.json`, not by editing them.

To put a real standalone build on a physical iPhone — including the free,
no-paid-membership route — see **[INTERNAL_TESTING.md](../INTERNAL_TESTING.md)**.
Note that `npm run ios:device` builds a *Debug* dev client that needs Metro
running; that document covers Release builds that run on their own.

## Brand assets

The mark is a crescent moon, matching the `moon` icon the app already renders in
the onboarding hero and the History empty state — so the launch image and the
first screen you see are the same shape.

`scripts/make-logo.py` generates it, so the geometry and colours live in code
rather than in a binary nobody can edit:

```bash
python3 scripts/make-logo.py     # needs Pillow
```

| File | Used by |
| --- | --- |
| `assets/logo.png` | the master mark, accent `#5B6CFF` on transparency |
| `assets/splash-icon.png` | splash screen, light mode |
| `assets/splash-icon-dark.png` | splash screen, dark mode, accent `#8B98FF` |
| `assets/icon.png` | iOS app icon — white mark on accent, **opaque, no alpha** |
| `assets/android-icon-foreground.png` | Android adaptive icon, masked layer |
| `assets/android-icon-background.png` | Android adaptive icon, solid accent |
| `assets/android-icon-monochrome.png` | Android themed icons, recoloured by the system |
| `assets/favicon.png` | web |

Two platform constraints the script encodes rather than leaves to chance: the
iOS icon must be opaque with square corners and no alpha channel, because iOS
applies its own mask and rejects transparent icons at submission; and the
Android foreground sits at a smaller scale, because launchers mask it to a
circle or squircle and only the middle ~66% is guaranteed visible.

The splash is configured through the `expo-splash-screen` config plugin in
`app.json`, with background colours matching `palette.bg` in both appearances.
Changing any of it needs `npx expo prebuild --platform ios` and a rebuild —
and note that a **Release** build is required to see the splash, because
development builds show the app icon instead.

## Data model

The form is user-defined, so the shape of an entry is not known until runtime
and cannot be expressed as typed columns. Everything is therefore kept in **one
table used as a document store**, with real columns only for what has to be
queried:

```sql
CREATE TABLE docs (
  collection TEXT NOT NULL,   -- 'form' or 'entry'
  id         TEXT NOT NULL,
  created_at TEXT NOT NULL,   -- ISO-8601 UTC
  updated_at TEXT NOT NULL,
  json       TEXT NOT NULL,   -- the document
  PRIMARY KEY (collection, id)
);
CREATE INDEX idx_docs_created ON docs (collection, created_at DESC);
```

Two collections:

| Collection | Documents | Payload |
| --- | --- | --- |
| `form` | exactly one, id `current` | `{ schemaVersion, fields: FormField[] }` |
| `entry` | one per check-in | `{ values: { [fieldId]: value } }` |

A `FormField` is a discriminated union on `kind`:

| Kind | Value type | Notable options |
| --- | --- | --- |
| `slider` | number | `min`, `max`, end labels, `goodEnd`, `chart` |
| `words` | string | `options`, `allowCustom`, optional link to a slider |
| `text` | string | `placeholder`, `lines`, `footnote` |
| `datetime` | ISO string | `emptyLabel`, `suggestPrevious` |
| `yesno` | boolean | `yesLabel`, `noLabel` |

Every field also carries `label`, `help`, and an optional `group` — consecutive
fields sharing a group render inside one card, which is how "Mood" holds both a
slider and a word picker.

### Three rules worth knowing

**Field ids are permanent.** Answers are stored against the id, never the label,
so renaming a field updates it everywhere including entries saved years ago.

**Deleting archives by default.** `archived: true` hides a field from new
check-ins while keeping its definition, so old entries still render. Erasing the
answers is a separate, explicitly confirmed action — without a definition there
is no way to interpret a stored value, so the two go together.

**Nothing read from disk is trusted.** `src/forms/normalize.ts` coerces whatever
JSON it finds into a valid form or entry and drops what it cannot salvage.
Documents come from three sources that can all disagree with the current code —
this build, an older build, and an imported backup file — so a single bad field
can never take a screen down with it. Unreadable JSON is skipped with a warning
rather than thrown.

Timestamps are stored as UTC and bucketed into local days in JavaScript, so
charts stay correct across timezone and daylight-saving changes.

### Migrations

`src/store/schema.ts` runs on every launch. All its DDL is `IF NOT EXISTS` and
runs unconditionally rather than being gated on `PRAGMA user_version`: creating
a table that already exists costs nothing, and it means a database stamped ahead
of its real schema repairs itself instead of failing every query.

Adding a field kind or an option needs **no migration at all** — it is JSON.
Only a change to the queryable columns does.

### The move off the old `logs` table

Earlier builds stored every tracked field as a column on a `logs` table. The
starter form reuses those exact column names as its field ids, so
`src/store/legacy.ts` migrates a row by reading each column into a value map.
Two properties make that safe to run on a journal someone relies on:

- **Deterministic ids.** A row with `logs.id = 7` always becomes entry
  `legacy-7`, so re-running replaces rather than duplicates.
- **Verify before stamping.** The "already migrated" marker is only written once
  the number of migrated documents matches the number of source rows. An
  interrupted run resumes on the next launch.

The `logs` table is deliberately left in place afterwards. It costs little and
it is the only copy of the original data if a mapping bug ever surfaces. Erasing
everything from Privacy & data drops it too.

## Backup and restore

The app has no account and no server, which makes a lost phone a lost journal —
so **Settings › Privacy & data** can write the whole thing to a JSON file:

```json
{
  "app": "mood-tracker",
  "formatVersion": 1,
  "exportedAt": "2026-10-31T12:00:00.000Z",
  "form": { "schemaVersion": 1, "fields": [ … ] },
  "entries": [ { "id": …, "createdAt": …, "updatedAt": …, "values": { … } } ],
  "settings": { "reminder_times": "09:00,14:00,20:00" }
}
```

The file is written to the app's **cache** directory and handed to the OS share
sheet. Nothing is uploaded: where it goes next is entirely the user's choice,
and the app never learns what they picked. The cache is the right home because
the file only needs to live long enough to be sent somewhere.

The format is deliberately readable rather than compact — a journal someone
keeps for years should not need this app to still exist to be legible.

Importing offers two modes:

- **Replace everything** — the real-restore path. The current form and every
  entry are discarded and the file becomes the truth.
- **Add missing entries** — keeps the current form and adds only entries whose
  ids are not already present. Any field the backup defines and the form does
  not is appended **archived**, so the imported answers stay readable in History
  instead of being dropped on read.

## Reminders

Reminders are scheduled entirely on-device — no server, no push token, no
account. They work offline and in the Simulator. Scheduling lives in
`src/lib/notifications.ts`; the times themselves are a separate pure module,
`src/lib/reminderTimes.ts`.

Three fire per day, defaulting to 9:00, 14:00 and 20:00 local
(`DEFAULT_REMINDER_TIMES`). **Each one is adjustable** from the Reminders screen
— tap a row to open a time picker. Changes are saved to the `settings` table
under `reminder_times` as `"09:00,14:00,20:00"`, kept sorted so the list always
reads top-to-bottom through the day. A malformed or missing value falls back to
the defaults rather than scheduling nonsense.

The title is always "Track your mood"; the body is drawn from a rotation
(`REMINDER_BODIES`) keyed on the calendar date, so consecutive days do not
repeat themselves. Pools are selected by **the reminder's actual hour**
(morning < 12:00, afternoon < 17:00, evening after) rather than by its position
in the list, so re-timing a reminder to the evening also re-themes its wording.

### Why sixty, and why it is topped up

iOS keeps at most **64 pending notifications per app** and silently drops the
rest, so the app schedules `MAX_SCHEDULED_REMINDERS = 60` individually dated
notifications and leaves the remaining slots free. At three a day that is a
**twenty-day runway**.

Because each one is a specific date rather than a repeating trigger, the queue
drains as reminders fire. `NotificationBootstrap` calls `scheduleLocalReminders()`
on every app launch to refill it, which pushes the twenty-day window forward.

Every scheduled reminder carries the times it was built from in its `data`
payload, so the queue describes its own configuration. A rebuild is skipped only
when the queue is both full *and* still matches the configured times — which
means launching the app repeatedly does no redundant work, while re-timing a
reminder always takes effect even though the queue was already full.

> **The trade-off:** if the app is never opened for twenty days, the queue
> empties and reminders stop until it is opened again. A repeating daily trigger
> would never expire but could not vary its wording. Rotating copy was the
> priority here; if you would rather have reminders that never lapse, swap the
> `DATE` triggers in `scheduleLocalReminders()` for three `DAILY` ones.

The **Reminders** screen (bell icon on the Log screen) has a picker for each of
the three times, a reset-to-defaults shortcut, permission state, how many
reminders are queued and how far ahead they reach, and a "send a test reminder"
button that fires one three seconds later.

## Using your personal Expo account (not `caitcommittee`)

EAS CLI stores its login **globally** in `~/.expo/state.json`, so `eas login`
switches accounts for every project on this machine. Two things keep this
project on your personal account without disturbing your other project.

### 1. A project-local access token

`EXPO_TOKEN` takes precedence over the stored login, so this project carries its
own credential:

1. Sign in to [expo.dev](https://expo.dev) as your **personal** account.
2. Create a token at **Account Settings → [Access tokens](https://expo.dev/settings/access-tokens)**.
3. `cp .env.eas.example .env.eas` and paste the token in. `.env.eas` is
   gitignored.

Then run every EAS command through the wrapper:

```bash
npm run eas -- whoami        # should print your personal username
npm run eas -- init          # creates the project under the personal account
npm run eas -- build --profile development --platform ios
```

`npm run eas` refuses to run if no token is present, so it can never silently
fall back to the globally logged-in account. Your other project keeps using
`eas` directly and stays on whatever `eas login` set.

### 2. Pin the owner in `app.json`

`owner` is the Expo account that owns the project. **If it is unset, it defaults
to whoever happens to be logged in** — which is how a project ends up on the
wrong account. Add `owner` to `app.json`, next to `slug`:

```json
{
  "expo": {
    "name": "Mood Tracker",
    "slug": "mood-tracker",
    "owner": "your-personal-expo-username"
  }
}
```

With `owner` set, EAS fails loudly instead of creating or building the project
under the wrong account.

### Then create the project

```bash
npm run eas -- init
```

This registers the project under your personal account and writes
`extra.eas.projectId` into `app.json`, which EAS uses to identify the project.
Reminders do not need it — they are scheduled on-device (see
[Reminders](#reminders)).

### Build profiles

`eas.json` defines:

| Profile | What it produces |
| --- | --- |
| `development` | dev client for a **physical iPhone** (needs Apple credentials) |
| `development-simulator` | dev client for the **iOS Simulator** (no Apple account needed) |
| `preview` | internal-distribution release build |
| `production` | App Store / TestFlight build |

```bash
npm run eas -- build --profile development-simulator --platform ios
npm run eas -- build --profile development --platform ios
```

You do **not** need EAS for a local dev build — `npm run ios` already builds and
runs one with your local Xcode, for free. Use EAS when you want a build without
local signing setup, or to install on a device over the air.

### Verifying which account you are on

```bash
npm run eas -- whoami        # this project (personal, via .env.eas)
npx eas-cli whoami           # global login (caitcommittee)
```

## Seeding the simulator

History and Trends are hard to judge against three hand-typed entries.

```bash
npm run seed                       # 60 days into the booted simulator
npm run seed -- --days 120 --seed 7
npm run seed -- --keep             # add to existing entries rather than replacing
```

This writes straight into the app's SQLite file instead of adding a "populate"
button to the app, so no seeding code can ever ship: there is no dev-only
branch to misconfigure, and the Release build already on the simulator needs
no rebuild to pick it up. Simulator only — it finds the container through
`xcrun simctl`, which has no equivalent for a physical device.

The form definition is imported from `src/forms` rather than hand-copied, so
generated answers always match the real starter form, including the per-score
word lists. Output is deterministic: the same `--seed` produces the same
journal, which makes a screenshot reproducible.

The data is shaped to look lived-in rather than uniform — mood drifts on a
slow random walk, fatigue tracks loosely against it, about one day in seven
has nothing logged, and the self-harm field is populated rarely and with
deliberately mild wording.

## Releasing to the App Store

```bash
npm run release:ios
```

That regenerates `ios/`, archives for device, and exports a signed `.ipa` to
`ios/build/ipa/` — the file you drag into Apple's **Transporter** app. Set
`destination` to `upload` in `scripts/ExportOptions.plist` to send it straight
to App Store Connect and skip Transporter entirely.

It runs entirely through local Xcode. EAS is not involved and no Expo account
is needed; `expo prebuild` only regenerates `ios/` from `app.json`.

### You need a paid Apple Developer Program membership

App Store signing requires an **Apple Distribution** certificate, which a free
account cannot issue — it only grants "Apple Development".

If you have never created one, that is usually fine: `-allowProvisioningUpdates`
makes `xcodebuild` create the certificate *and* the provisioning profile on
demand, using the Apple ID signed into **Xcode › Settings › Apple Accounts**.
That is far less painful than doing it by hand in the developer portal. The
script notes the missing certificate and continues, because stopping would
prevent the very thing that fixes it.

To tell a paid account from a free one: **Xcode › Settings › Apple Accounts ›
Manage Certificates… › +**. If **Apple Distribution** is on the menu you are
on a paid membership; a free account offers only development certificates. A
paid team also shows a **Role** and a "Certificates, Identifiers & Profiles"
row, where a free one is labelled "Personal Team".

Note that `-allowProvisioningUpdates` is an `xcodebuild` command-line flag,
already included in `scripts/release-ios.sh` — it is not a setting anywhere in
the Xcode UI.

### Two failures worth recognising

**`Signing for "MoodTracker" requires a development team.`**

`expo.ios.appleTeamId` is missing from `app.json`. `-allowProvisioningUpdates`
can create certificates and profiles, but it still has to be told which team
to create them under, and prebuild leaves `DEVELOPMENT_TEAM` empty without it.
Your team ID is the `OU` field of any Apple certificate you hold — not the
value in parentheses after your name, which is the certificate's own ID:

```bash
security find-certificate -c "Apple Development" -p \
  | openssl x509 -noout -subject -nameopt multiline
```

**`Unable to load contents of file list: ...xcfilelist`** — for files that are
plainly on disk.

Stale DerivedData. `prebuild --clean` rebuilds `ios/Pods` from scratch, so a
build description cached in the shared
`~/Library/Developer/Xcode/DerivedData` can outlive the Pods tree it
describes. The release script uses a private `build/DerivedData` and empties
it before each archive. If you hit this from the Xcode GUI instead, delete
the project's folder under the shared DerivedData directory.

### Where build output goes

Everything the release produces lands in `/build` at the repo root — archive,
DerivedData, and the exported `.ipa` — and `/build` is gitignored. It is
deliberately *not* under `ios/`, because `prebuild --clean` deletes `ios/`
wholesale on every run: a multi-gigabyte DerivedData tree there would be
re-deleted each release, and the delete fails outright with `ENOTEMPTY` if
Xcode still holds a file open.

### Version bumping stays manual

`build.production.autoIncrement` is `false`. With the `local` version source,
Expo's Xcode build phases will otherwise rewrite `expo.ios.buildNumber` in
`app.json` during an archive, so a release silently dirties your working tree
and the number you shipped is not the number you committed. Bump it yourself;
the script reminds you each run.

### Bump the build number for every upload

App Store Connect rejects a duplicate build number for the same version, and
it is a common cause of a failed upload. Before each one, increment
`expo.ios.buildNumber` in `app.json`:

```json
"ios": { "buildNumber": "2" }
```

Two settings make this behave predictably, and both matter:

- **`expo.ios.buildNumber` must be set.** Without it, `expo prebuild` writes
  `CFBundleVersion = 1` on every run, so the second upload always collides.
- **`cli.appVersionSource` is `local`.** Under `remote`, EAS stores build
  numbers on its servers and *ignores* the value in `app.json` — so the two
  workflows would silently disagree about what you just shipped. If you later
  move to EAS builds, `eas build:version:sync` reconciles them.

`app.json` also declares `ITSAppUsesNonExemptEncryption: false`, so App Store
Connect does not ask the encryption question on every upload.

## TestFlight

```bash
npm run eas -- build --platform ios --profile production
npm run eas -- submit --platform ios --latest
```

(Use `npm run eas` rather than a bare `eas` so the build goes to your personal
account — see [Using your personal Expo account](#using-your-personal-expo-account-not-caitcommittee).)

`app.json` already sets the bundle identifier
(`com.kalobtaulien.moodtracker` — change it if you like) and declares
`ITSAppUsesNonExemptEncryption: false` so App Store Connect does not ask the
encryption question on every upload.

`eas.json` pins the App Store Connect identity under `submit.production.ios`:

| Field | Value | Why |
| --- | --- | --- |
| `sku` | `moodtracker` | A permanent, store-invisible ID for the app. EAS generates a random one unless it is set, so pinning it keeps resubmissions pointing at the same ASC record. |
| `bundleIdentifier` | `com.kalobtaulien.moodtracker` | Usually autodetected; set explicitly so credential lookup cannot pick the wrong target. |

`appName` and `language` are deliberately left out — they default to
`expo.name` and `en-US`, which are already correct.

## Privacy (implementation notes)

Entries never leave the device. The app makes no network calls with your journal
and has no server component, so there is nothing to receive your data. The
database file sits in the app's private container and is included in encrypted
iPhone backups. Uninstalling the app deletes the database.

This is stated in the app too, in plain language, on **Settings › Privacy &
data** — alongside the backup export, the importer, and an erase-everything
button.

The one path by which data can leave the device is the backup export, and it
only goes where you send it: the app writes a file and hands it to the share
sheet, which means the destination is the OS's business and not the app's.

If you would rather read the raw database, pull it out of the app container with
Xcode's Devices window — it is plain SQLite, with each document's payload in the
`docs.json` column. See [Data model](#data-model).
